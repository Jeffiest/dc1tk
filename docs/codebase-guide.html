The Dark Chronicle script codebase

Welcome. You've been handed extracted/scripts/: about 2,500 C files that make up the gameplay code of Dark Chronicle (Dark Cloud 2). This guide walks through that codebase the way you'd learn any game's scripting layer: what each system is, where its code lives, how the pieces call each other, and how to make the changes you'll actually be asked for.

About the code on this page The repository never stores the game's own code or text, so excerpts from extracted/scripts/ here are short and abridged (... marks cuts) with dialogue left out. Each excerpt names its file so you can read the whole thing in your own tree. Code in the task walkthroughs is new code written for this guide.

Part 1 · Orientation

1The big picture

The game is split in two. The engine (the PS2 executable) draws the world, runs physics and collision, plays animations and sound, and owns the data tables. The scripts decide what happens: every cutscene, conversation, door, chest, monster brain, the player's sword combo, and how each spell or explosion moves. Scripts call into the engine through about 1,100 engine functions called natives, and the engine calls into scripts by starting their programs when something happens.

2Rules every script follows

All five kinds share one shape. Learn it once and every file reads the same way.

  1. 1
    Every file and function has a comment saying what it does. They were written by this project (the shipped bytecode had none). Read them first.
  2. 2
    The first header says which kind of script this is (monster.h, event.h, action.h, effect.h, arg.h) and declares every native it can call. pal.h names the save flags, music and sounds; disc.h names monster kinds, items, NPCs, animations and effects.
  3. 3
    Globals live as long as the script stays loaded and start at 0 each load. Note that the Golem declares spawn_x only because a library it includes writes to it.
  4. 4
    The PROGRAM table is the script's list of entry points. The engine starts init when the monster spawns, update every frame after, damage when it's hit hard, and so on. Nothing else in the file runs unless one of these calls it.
  5. 5
    #include "lib/..." pastes shared code in at that spot, exactly as the original source did. Most of what a script does is in its libraries. Libraries may use the including script's globals and functions.
  6. 6
    wait; is how time passes. A program runs until it waits, gives up the rest of the frame, and carries on from the same spot next frame. The helper here wraps a wait;.

Programs are coroutines

25 frames a second The PAL game draws a frame every other 50 Hz vertical blank (mgFrameRate 2), so wait; is 1/25 s; the scripts were written for the NTSC game's 30. Some retail map libraries' wait_frames(n) quietly scale n by 50/60 (5/6), monster libraries use scale_frames_to_pal, and the fades take 5/6 of their frames too. The mod library's modkit_wait(n) does not scale. When numbers feel off by 20%, this is why.

Three layers of "function you can call"

  • Natives (place_monster, show_message): engine functions, declared and documented in sdk/*.h. Hover them in your editor.
  • SDK helpers (init_chara_actor, set_camera_view, spawn_effect_at): small inline wrappers in sdk/helpers/.
  • Runtime library functions (wait_frames, talk_to_npc, play_voice_message, chase_target_steps): game code in lib/. These only exist in scripts that include the library, so code you move to a new file may need to include it too.

3Where everything lives

Folders keep the game's own codes, with an English name after them. Commands take the short code (g01, e33a).

extracted/scripts/ ├── map/ every place in the game, one script per map │ ├── g/ g01_sindain/ … Georama towns (present day); interiors in subfolders: i07_dwarves_house/ │ ├── m/ m01_palm_brinks/ … Palm Brinks at different points in the story │ ├── i/ i04_houses/h01_…/ … Palm Brinks interiors (shops, station, houses, clinic) │ ├── f/ f01_jurak_mall/ … future towns │ ├── s/ s51_raybrandt_castle/ … story maps: stations, chambers, flashbacks, event copies of towns │ └── d/ d01_underground_channel/ │ ├── d01_1.c … d01_5.c THE dungeon script: runs every floor of d01 │ ├── d01_sfida_1.c … Spheda (golf) bonus mode │ ├── b01_channel_reservoir/ fixed special map: usually a boss arena │ └── e01_channel_entrance/ entrance hub, runs like a town ├── dungeon/ │ ├── monster/ e33a_golem.c … 144 monster AIs (e = enemy, b = boss/story) │ ├── eff_script/ m_shockwave.c … effects │ ├── act_script/ f10a.c … Monica's monster forms, the Ridepod, old player builds │ ├── articles/, sphida/ more effects, packed inside model files │ └── sys_script/ older per-dungeon scripts (see below) ├── mainchr/ c01_max.c, c02_monica.c the two heroes in combat ├── event/ arg data tables, the chest explosion effect ├── lib/ shared code, mirroring the folders above └── include/disc.h names from your disc: monsters, items, NPCs, motions, effects

Five copies of every map script

Map scripts come per language: g01_1.c is English, _2 to _5 are French, German, Italian and Spanish, and g01.c with no number is the original Japanese, which the PAL game never runs. The game loads the one matching the console's language. The same goes for libraries: base_town_villagers_v1.c to _v5.c are the same code with each language's text, and g01_2.c includes _v2.

Change all five, or test in English An edit to g01_1.c only shows on an English console. For anything you ship, make the change in all five files, or put it in one library that all five include.

Other file-name patterns

  • g01b_1.c, g01c_1.c, rush_g01_1.c: alternate scripts for the same map. A running script swaps one in for a story beat (load_event_script("g01/g01b_1.stb", 501)) and swaps back after.
  • i04h01a … i04h01f: separate builds of one room (Max's room at different story points), each a real map.
  • lib/map/g/g01_sindain/: code shared by the g01 scripts. lib/map/ root: code shared across many maps (the villager talk runtime, game over, menus). Each library's top comment lists who uses it.
  • dungeon/sys_script/: one script for each of d01–d05, without language variants. Nothing in the tree loads them and their chest code calls a native that does nothing in the retail game, so they look like an earlier generation of the dungeon scripts. The code that runs is map/d/dNN/dNN_1.c.
Part 2 · The systems

4Towns and story maps

A town script is a set of handlers. The player walks around freely; the engine calls the script when they enter, talk to someone, use a door, stand in a time gate or save point. Each handler runs as an event: player control pauses until it returns.

At the bottom of each branch the line itself is shown. In the PAL scripts most town talk is literal text in the script, then a library call that opens a speech bubble from the speaker and waits for the button: 

show_message(0, "...");             // the line, as text (with \n and <page> codes)
talk_to_npc(npc_slot, -1, 0, 0);    // -1 = show what's laid out; bubble, wait, finish_event

The other form is a number: show_message(0, 500010) shows line 500010 of the message file the scene loaded. The decompiler puts that line's text in a comment beside the call so you can search for it. Yes/no and menu choices are lines of one message, read back with ask_question_at or ask_npc_question: 0 for the first option, -1 for cancel.

Georama towns (g/) use a different library, lib/map/g/town_npc_talk_and_shop_v1.c, with the same idea.

Doors and trigger points

Trigger points are drawn into each map's .map file: a door, a spot to step on, a spot to press the button at. Each one names a program number. dc2tk map extracted/scripts g01 lists them all, for example "door to g01i07, runs program 200", with the part each belongs to: the placement that carries it (a point of a template is listed once for every placement of it) or the map's own. Scripts switch points on and off with set_func_point_enabled(part, "door", on) (part "" for the map's own points), which is how a house stays locked until a story flag is set. Inside the program, get_event_data(EVENT_DATA_ARG1, &x) reads the point's argument.

5Dungeons

Dungeon floors are random, so there is no script per floor. One script runs a whole dungeon: map/d/d01_underground_channel/d01_1.c (and its four translations) handles every floor of the Underground Channel: floor setup, gates, keys, chests, the floor-clear celebration, game over, and the story floors that jump elsewhere.

Setting up a floor

Floor monsters are data, not code With one argument, load_monster_data ignores it and loads the current floor's monster list from engine data. MONSTER_SEWER_RAT is only how the decompiler prints the number 0. So you won't find "the Golem appears on floor 9" in any script, and xref monster golem reports no placements. Scripted fights are different: they name exact kinds (see below). The floor lists are dungeon/cfg_file/mos_place<dungeon>.cfg, which a mod changes as the data:floors table (game data).

Event mode: why dungeon handlers must be short

When a dungeon program starts, the dungeon enters event mode until it ends, and the player can't move in event mode. So a dungeon handler that loops with wait; freezes the player for as long as it runs. A handler that never waits runs inside a single frame and play carries on. Retail handlers also pause chosen parts of the dungeon with set_dungeon_pause(DNG_PAUSE_MONSTER_AI | ..., 1) while a chest or door animation plays, and unpause after.

Story fights and boss arenas

Fixed fights happen on special maps: the bNN_*/ folders inside a dungeon, or story maps like s51. They load and place exact monster kinds, and they end when a monster asks the map to run a program:

The ending lives in the monster's script, which matters when you change a fight (see task 13). The other way a fight ends is a monsters_cleared program in the map, which the engine runs once the floor is empty.

Leaving, and game over

Boss rooms go back to the dungeon with load_event_script("d01/d01.stb", talk_or_dungeon_start); dungeons go to towns with go_to_edit_mode(map_id, program). Game over is run_game_over(...) in the lib/map/base_game_over_vN.c runtime: it offers a character switch if one is possible, otherwise shows the game over screen. Each map's player_dead program calls it.

6Cutscenes

A cutscene is just a long map-script function. They live in the map's libraries (lib/map/s/s51_raybrandt_castle/gaspard_time_gate_scene.c holds play_event_50) and are called from a program. Every retail scene has the same five phases:

  1. 1
    Setup. Set the "seen" flag, reset the event state, load music, the message file and the models the scene needs, and bind actors to them.
  2. 2
    Open the skip window.
  3. 3
    The timeline. Camera moves, actor moves and animations are queued and play out over the following frames. The script waits on them with polling helpers (wait_object_script, wait_camera_script, wait_frames).
  4. 4
    skip_end; While the player skips, the engine stops running natives until the script reaches this line. Anything between enable_scene_skip and here may not happen, so never put a flag, a warp or cleanup in that stretch.
  5. 5
    Teardown. Unload what was loaded, give the player back their character and camera, finish_event(). Flags and warps that lead to the next scene usually live in the caller.

Slots, handles and actors

  • Scene slots hold models. Slot 0 (CHARA_PLAYER) is whoever the player controls, 1–5 are their weapons, 8–31 are the map's villagers, and scenes load their own models into free slots with load_scene_chara, load_inactive_chara, copy_chara.
  • Handles (0–31) point at a slot or a map part (bind_handle_map_part: a door, a window, a sword on the wall).
  • Actors are command queues that drive a handle. init_chara_actor(a, slot) sets up all three with the same number. Every *_actor_* call adds to the queue; check_actor_busy(a) says whether it's finished.

Camera

Positions are the eye (x, y, z) then the point looked at, in world units with y up. cut_camera cuts instantly (clearing queued moves); move_camera_to(..., frames) glides; move_camera_eased(..., frames, ease, rate) eases; attach_camera_to_actor follows someone. After the scene, reset_camera(CAMERA_RESET_ACTIVE) hands control back to gameplay.

Text and voice

Scene lines are message ids from the file the scene loaded: id = event × 10000 + n (500010 is event 50's first line). Voiced lines use the same number for the audio stream, and the runtime library's play_voice_message(id) plays the voice, shows the caption, animates lips and waits. Unvoiced town scenes often use literal text with show_message(0, "...") and a bubble helper.

7Monsters

Kinds, models and AI scripts

Every monster in the game is a kind: a row in the engine's monster table giving its name, model, stats and the AI script it runs. include/disc.h lists them all: 

MONSTER_GOLEM = 168,  // model e33a, AI e33a
MONSTER_RAVE_GOLEM = 169,  // model e33b, AI e33a
...
MONSTER_GRIFFON_SOLDIER = 37,  // model e254a, AI e254a
MONSTER_GRIFFON_SOLDIER_523 = 523,  // model e254a, AI b254a
  • File names are the AI code: e33a_golem.c is AI e33a. e files are ordinary enemies, b files bosses and story fights. The letters a–d are a family's four colour variants, which usually all run the a AI.
  • One AI often serves many kinds. Editing e33a changes all four golems; element runs twenty kinds. Branch on get_monster_kind() when you need one to differ.
  • Story-fight kinds often have their own AI. Kind 523 looks like a Griffon Soldier but runs b254a, so the castle fight can count deaths without changing every Griffon Soldier in the game.
  • About 30 AI files are dead: no kind runs them (for example e111a–e115a, whose models run eJema). Check with dc2tk xref extracted/scripts monster NAME before editing.

Tuning knobs

  • set_defense_rate, set_guard_rate(-1, r), set_dodge_rate(-1, r): scale the table's values for this monster (-1 means "me").
  • set_mask_flag(MASK_NO_GUARD / MASK_NO_DODGE, on): switch off the engine's guard or dodge rolls. Scripts lock both during their own scripted moves.
  • get_rage_hits_left(): hits left before the monster enrages (-1 for bosses).
  • get_life(&f) (0–1) and set_life: bosses use these for phase changes.

Bosses

Boss scripts (b08a_emperor_griffon.c, b13a_arch_demon.c) are long, 2,500–3,300 lines, and add: a custom camera (set_camera_mode(CAMERA_MODE_BOSS)), helper monsters (create_monster), phase changes checked inside every wait (when life drops below a mark, the boss calls run_event_script for a mid-fight scene), and a death program that hands the ending to the map.

8The player

mainchr/c01_max.c and c02_monica.c are the heroes in combat, built like monster scripts but driven by the pad. init registers the hit windows for each weapon model; update is a state machine whose state is a 16-bit "saved value":

9Effects

An effect script is a tiny program: play runs from the moment the effect is created and moves its sprites or model every frame; the effect is deleted when play returns. finish runs if the creator asks it to stop. The creator passes data in through two work vectors and eight values. Effects can do damage themselves, which is how a monster's shockwave hurts the player.

Map scripts start effects too (load_effect_script, then create_effect(name, owner, &slot)), as do the player scripts (Max's charge attack creates EFFECT_MAX_CHARGE_ATTACK). Many effect bodies live in lib/dungeon/*.c because the same effect exists both in eff_script/ and packed into articles/eff01.chr.d/.

Part 3 · Doing the work

10Your working loop

Never edit extracted/scripts/ in place for real work. Put changes in a mod, a folder in mods/ holding only the files you change or add. The tree stays clean, and mods can be combined.

  1. Find the code. Use the lookup commands, the comments, and your editor (open extracted/scripts/ in an editor with clangd for hover docs and go-to-definition).
  2. Copy it into a mod. 
    dc2tk mod new extracted/scripts my-change map/g/g01_sindain/g01_1.c
    Then edit under mods/my-change/files/.
  3. Or add without copying. A mod's mod.json can add programs and includes to a map's scripts (all languages at once), or wrap an existing program with your functions before or after it. See task 14. A patch goes further: a .c file with #pragma target map g01 (or script, monster, library) holding only the functions it overrides or adds, merged into every script it targets. dc2tk mod override extracted/scripts my-change FUNCTION --map g01 starts one, and dc2tk mod slim turns copied files into patches (modding.md).
  4. Build and play. 
    dc2tk build extracted/scripts dc2.iso -o modded.iso --mod my-change --play
    Only the scripts that change are recompiled, so this takes seconds.
  5. Jump straight to the scene. --start-at s51:story_50 (or "start_at" in mod.json) makes New Game start there, on maps loaded dungeon-style. A town map works too, entered as the game enters towns: --start-at g01 starts in Sindain at map_start, as Max. Either way it is a new game's save, with no story flags set, so a scene that waits for one won't play; for those, keep a PCSX2 save state near the spot.
You can change files, not add them build replaces scripts that exist on the disc. A brand-new script file (say dungeon/monster/e999a.c) is skipped with "not on the disc", because nothing in the game would load it. New library files are fine, since they're pasted into existing scripts. Keep yours under lib/mods/NAME/. The one new script a mod can have is a new map's own: a map added under "add" in mod.json takes a "script", which build compiles where the engine looks for it (maps, section 9).

11Task: change what an NPC says

Change Gordon's early line in Palm Brinks

The pattern for any "this character should say something else" ticket.

  1. Find the character's handler. Search the tree for a phrase from the line, or for the character's name in function names (talk_gordon). If you only know the map, read its talk_or_dungeon_start program and follow it into the library.
  2. Find the right branch. Read the if chain on flags and quest state (talk_gordon → talk_gordon_early) until you reach the show_message for the case you want.
  3. Check who else uses the code. The library's top comment lists the scripts that include it. base_town_villagers_v1.c is included by several Palm Brinks maps, which is usually what you want for a villager: their line changes everywhere.
  4. Edit the text in every language copy. Copy the five libraries into a mod and change the literal in each: 
    dc2tk mod new extracted/scripts gordon-line lib/map/base_town_villagers_v1.c lib/map/base_town_villagers_v2.c lib/map/base_town_villagers_v3.c lib/map/base_town_villagers_v4.c lib/map/base_town_villagers_v5.c
    Use \n for a new line and <page> for a page break; the message text codes list button icons and placeholders. Keep lines short enough for the bubble.
  5. If the line is a number, not text (show_message(0, 1090010)), it comes from the message file the scene loaded, the event text beside the scripts on the disc, which these tools don't convert (a file: line in mod.json can only replace it whole). Replace the number with your own literal string. If it was voiced, also remove or replace the voice call, or the old audio plays under your new text. (The menus', shops' and system messages are the other kind of message file, .mes, which a mod does edit, by text: id: message files.)
  6. To change it on one map only, give that map its own copy of the library first: dc2tk fork extracted/scripts lib/map/base_town_villagers_v1.c lib/mods/gordon/villagers_m01_v1.c map/m/m01_palm_brinks/m01_1.c.

12Task: make an enemy behave differently

Make the Golem hit harder and react sooner

The pattern for "this enemy is too easy / should also do X".

  1. Find its AI and who shares it. 
    dc2tk xref extracted/scripts monster golem
    This prints the model, the AI file (dungeon/monster/e33a_golem.c), and the other kinds that run the same AI (Rave Golem, Rock Taster, Titan). Your change will reach all four unless you branch on get_monster_kind().
  2. Copy it into a mod. 
    dc2tk mod new extracted/scripts stronger-golem dungeon/monster/e33a_golem.c
  3. Change what's in the script itself. The useful knobs:
    • Hit size and timing: the radius and the start/end fractions in add_attack_hit in on_init.
    • Hit type: swap HIT_KNOCKBACK_ATTACK for another HIT_* from disc.h. Only existing damage settings work.
    • When it engages: the distances in choose_behavior_by_aggro (280.0 + 50.0, 230.0).
    • Toughness: set_defense_rate, set_guard_rate.
    • New moves: write a function like chase_and_swing_at_target using animations the Golem's model has (use the MOTION_* names already in its script) and call it from the behaviour choice.
  4. If you need to change a library function (say init_monster_ai's aggro range), fork the library for this script only. Editing monster_ai_full_toolkit.c itself would change 36 monsters: 
    dc2tk fork extracted/scripts lib/dungeon/monster/monster_ai_full_toolkit.c lib/dungeon/monster/golem_toolkit.c dungeon/monster/e33a_golem.c
  5. Build, then find a Golem. They roam random floors, so either play to one or put some in a scripted fight you can reach with --start-at (next task).
Not in a script's reach HP, attack power, the ABS and money it gives, and drops are in the engine's monster table. Scripts can scale how a monster takes damage (set_defense_rate) and read its power (get_attack()), but can't edit the table. A mod can, beside its scripts: dc2tk mod asset dc2.iso stronger-golem data:monsters writes the table into the mod as data/monsters.json with its mod.json line, and every value you change there ("hp" of {"id": 168, ...}) is patched into the built image's executable; the rest changes nothing. That changes every monster of kind 168, wherever it appears (game data, section 4).

13Task: a new enemy in a fight

What "new enemy" can mean here

You can't add a monster kind: kinds are rows in the engine's table, which a mod can change (data:monsters: stats, model, the AI script a kind runs) but not add to, and a new AI file is never built. What you can do covers most requests:

RequestHow
"Put enemy X in this fight"Place an existing kind from the fight's map script
"A new enemy with its own behaviour"Place an existing kind and rewrite an AI it runs. Pick an event-only kind (500+ with its own b AI) so the ordinary version elsewhere is unchanged.
"Extra enemies on a random floor"Call load_monster_data(kind, 0) and place_monster(kind, …) in the dungeon's floor setup, after the floor's own spawn

Recipe: replace the castle soldiers with Golems

  1. Find every place the fight is set up. dc2tk xref extracted/scripts monster 523 shows the soldiers placed in two functions: start_castle_battle (program 500 of map/s/s51_raybrandt_castle/s51_1.c to _5.c, reached from dungeon 1) and start_monica_gear_battle (program story_50, in lib/map/s/s51_raybrandt_castle/monica_gear_battle.c). Copy the five scripts and the library into a mod and change both.
  2. Swap the kind. Load the new kind (the 1 clears what was loaded before), then place it: 
    load_monster_data(MONSTER_GOLEM, 1);
place_monster(MONSTER_GOLEM, -382.5, -0.2, 120.2, 0.0, 1.61, 0.0);   // x, y, z, then rotation
place_monster(MONSTER_GOLEM, -428.0, -0.2, 202.7, 0.0, 1.71, 0.0);
...
    To mix kinds, load the first with 1 and the rest with 0. place_monster only works on dungeon-style maps.
  3. Fix how the fight ends. This is the step people miss. The soldiers' own AI ran event 510 when the fourth one died; Golems don't do that, so the fight would never end. Add a program the engine runs when the floor is empty: 
    PROGRAM(monsters_cleared, start_georama_with_starter_items);   // beside PROGRAM(510, ...)
    Or make the Golem's death program count kills and call run_event_script(510) like the soldier does, guarded by a flag that only this fight sets so Golems elsewhere aren't affected.
  4. Test it directly. story_50 runs start_monica_gear_battle, which also gives Monica her gear: 
    dc2tk build extracted/scripts dc2.iso -o test.iso --mod castle --start-at s51:story_50 --play

To give the castle Golems their own behaviour too, combine this with task 12: copy e33a_golem.c, fork its toolkit, and check your fight's flag with get_dungeon_flag wherever the castle version should act differently.

14Task: add a cutscene to a town

Play a short scene the first time the player enters Sindain after this point

A complete mod that touches no game file: one new library and a mod.json.

  1. Pick a free flag. The game uses save flags up to 824. Check yours is free with dc2tk flags extracted/scripts --flag 1300. Or let build choose: NEW_FLAG(FLAG_SINDAIN_HELLO_SEEN); in one of the mod's patches or headers (outside files/) gets a number nothing else uses, kept from build to build in mods/numbers.json (usage). Only the mod's sources outside files/ see that name: build compiles whole files under files/, like the library below, without the mods' numbers and refuses one that asks for a number, so the library writes its flag by hand.
  2. See what the map already does on entry. dc2tk map extracted/scripts g01 lists its programs, trigger points and free program numbers (9000 and up). Read its map_start so your scene doesn't fight a story scene that also auto-plays there.
  3. Write the scene as a library. mods/sindain-hello/files/lib/mods/sindain-hello/hello.c: The shape follows section 6, cut down: a flag set before anything can fail, init_event, actors, camera, a line, then camera back and finish_event. The modkit libraries give you text and waits without depending on a map's runtime library. Check every native and helper against sdk/event.h as you write (hover in the editor); the motion names must be ones the player's model has.
  4. Hook it in with mod.json. Wrapping map_start runs your function after the game's own, in the five language scripts of g01, without copying any of them: 
    {
 "additions": [
  {"scripts": ["map/g/g01/g01_?.c"],
   "includes": ["lib/mods/sindain-hello/hello.c"],
   "wrap": {"map_start": {"after": ["play_sindain_hello"]}}}
 ]
}
    "scripts" takes disc paths (codes without the readable names) and ? stands for the language digit. The shorter "map": "g01" would also reach every other script of the map: the g01b and g01c alternates, the rush script, and the interiors in its folder, so the scene would play inside the Dwarves' house too. An "after" function never runs if the program it wraps warps to another map, so check what map_start does first. To trigger it from somewhere else instead, add it as a program ("programs": {"9000": "play_sindain_hello"}) and warp to it: jump_to_map(-1, "g01", 9000).
  5. Build and play. --start-at g01 would start a new game in Sindain, but with no story flags set, so this scene (which waits for the Rococo flag) wouldn't play; play to Sindain or use a save state: 
    dc2tk build extracted/scripts dc2.iso -o modded.iso --mod sindain-hello --play
Going further For a scene with its own characters, follow the retail setup phase: load models into free scene slots, bind actors, and tear everything down after. If the scene must be skippable, wrap the timeline in enable_scene_skip() … skip_end; disable_scene_skip(); and keep every flag and cleanup outside it. The mods in docs/examples/ are fuller ones (a new map with a script of its own behind a door, a character made in Blender waving in a scene), and dc2tk mod test runs a mod's logic without the game.

15Task: tune the player

Make Max's combo more forgiving

  1. Copy Max into a mod: dc2tk mod new extracted/scripts max-combo mainchr/c01_max.c.
  2. Widen the chain windows. In update_sword_combo_model_0 (and _1, _2: one per weapon model), each hit has a test like progress >= 0.33 && progress <= 0.45. Lower the start or raise the end.
  3. Damage and reach are in setup_max_attacks: in add_attack_hit("dcol00", "dcol01", HIT_…, radius, power_rate, MOTION_…, start, end), raise power_rate for more damage, widen start–end for a longer active window. Again, there's a block per weapon model.
  4. The charge attack starts when the button is held longer than a frame count (get_attack_hold_frames() > 8 in the first hit, > 12 from standing). Its states are in lib/max_charge_attack.c, shared with the other Max scripts in dungeon/act_script/.

16Gotchas checklist

Run through this before calling a change done.

  • All five languages. Did the change go into _1 to _5 (or _v1 to _v5), or into one library they all include?
  • Library reach. Did you edit a file in lib/? build lists the other scripts it reached. Fork it if that's not intended.
  • Shared AI. Does your monster script run for other kinds too? Is it one of the dead AI files?
  • Fight endings. If you changed who is in a fight, does something still end it (a monster's run_event_script, or monsters_cleared)?
  • Skip window. No flag, warp or cleanup between enable_scene_skip() and skip_end;.
  • Natives never wait. Every "wait until" is a loop with wait; in it.
  • Dungeon handlers freeze the player while they wait.
  • Frame counts. Retail wait_frames scales by 50/60; modkit_wait and bare loops don't.
  • Asset names are exact. MOTION_*, HIT_* and EFFECT_* stand for Japanese strings the engine looks up. MOTION_ATTACK_1 and MOTION_ATTACK_1_2 are different strings (half- and full-width digits). Use the constants the model's own script uses; a wrong one silently does nothing.
  • Effects must be loaded (load_effect in init) before they're spawned.
  • Flags. New flags come from 825–2046 (NEW_FLAG hands them out from 1024); 2047 belongs to --start-at. Clear scene-only flags when the scene ends and on game over.
  • Message window 0 stays open after an event ends in a dungeon until something closes it.
  • New script files aren't built. Only new libraries included by existing scripts, and a new map's own script.
